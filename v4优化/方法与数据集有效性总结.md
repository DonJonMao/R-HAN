# 方法与数据集有效性总结

更新时间：2026-04-06

## 1. 总体原则

我们目前最大的经验不是“同一个 stage2 方法可以统一覆盖所有数据集”，而是：

1. 不同数据集的错误形态不同。
2. 不同任务上，“什么算 challenger”也不同。
3. 因此后续方法设计必须按任务类型分层，而不是继续追求单一通用协议。

当前最重要的任务维度可以分成五类：

- 数值推理：`gsm8k`
- 代码生成：`humaneval`, `mbpp`
- 选择题：`mmlu`
- 图结构推理：`nlgraph`
- 结构化列表 / 填空：`knowledge_crosswords`

## 2. 各方法对各类数据集的适用性

### 2.1 `v4.1`：显式 challenger + DAR + 严格 override

核心作用：

- 先压住错误 override
- 建立安全 challenger 通道

适用性判断：

- `gsm8k`：中等有效。它能先把错误翻案压住，但会严重 preserve-only。
- `humaneval / mbpp`：偏弱。代码任务需要的不只是安全 gate，还需要更强的 challenger 生成。
- `mmlu`：可用，但主要价值仍然是保守，不会带来太多收益。
- `nlgraph`：可用，但只能解决安全性，不能解决真正的结构搜索不足。
- `knowledge_crosswords`：可用，但对 slot-level 错误帮助有限。

结论：

- `v4.1` 适合作为安全基线
- 不适合作为长期主线

### 2.2 `v4.2`：软性 challenger 晋升 + ACH + calibration

核心作用：

- 放宽 challenger 供给
- 把最终仲裁从 pairwise 提升到结构化假设检验
- 做 judge 去偏校准

适用性判断：

- `gsm8k`：有限有效。它能让系统从“完全僵住”变成“偶尔进入 adjudication”，但收益仍然没有出来。
- `humaneval`：当前证据显示失效。到目前为止，连 `provisional challenger` 都没有出现。
- `mbpp`：高风险，预计比 `humaneval` 稍好，但若不引入 code-specific challenger，整体上仍偏悲观。
- `mmlu`：理论上价值有限。MCQ 的 challenger 不是靠更复杂的假设晋升，而是靠更好的证据判断。
- `nlgraph`：可能比 `gsm8k` 更合适，因为存在可靠 checker，但仍取决于 challenger 是否能形成真正的结构化差异。
- `knowledge_crosswords`：不稳定。少数派候选未必是真正有价值的“挑战”，因为局部字段错误很容易被整体 preserve 掩盖。

结论：

- `v4.2` 不是普适失败
- 但它明显不是 code task 友好的通用方案

## 3. `v4.3` 当前设计的适配性

参考设计见 [`v4_design.md`](/mnt/nvme/projects/R-HAN/v4优化/v4_design.md#L446)。

当前 `v4.3` 的核心是：

- 局部分支扩张
- restart
- 稀疏动态执行

### 3.1 当前 `v4.3` 最适合的任务

#### `nlgraph`

最友好。

原因：

1. `nlgraph` 本身有较可靠的 checker，并且偏好紧凑的 `coder-reasoner-verifier` 结构，见 [profiles.py](/mnt/nvme/projects/R-HAN/mas_treesearch/profiles.py#L410)。
2. 图结构错误通常可以局部定位。
3. 很适合通过局部分支扩张与局部验证来形成更强 challenger。

判断：

- `v4.3` 对 `nlgraph` 最可能真正起效。

#### `gsm8k`

中等友好。

原因：

1. `gsm8k` 的失败往往来自局部推理路径错误。
2. restart 和局部扩张有助于打断错误链条。

判断：

- `v4.3` 对 `gsm8k` 仍然有意义
- 但提升幅度未必像 `nlgraph` 那么直接

### 3.2 当前 `v4.3` 部分友好的任务

#### `mbpp`

部分友好，且比 `humaneval` 更友好。

原因：

1. `mbpp` 是 code generation，但任务短、测试更显式。
2. 局部 patch / restart 更容易在短程序里成立。

判断：

- 如果 `v4.3` 只保留通用版本，它在 `mbpp` 上仍有一定希望
- 但要真正稳妥，仍应加入 code-specific 的 challenger 构造

#### `humaneval`

部分友好，但风险较高。

原因：

1. `humaneval` 是 code generation，见 [profiles.py](/mnt/nvme/projects/R-HAN/mas_treesearch/profiles.py#L584)。
2. 任务更长，程序空间更大，局部错误不如 `mbpp` 那样容易被简单 restart 修复。

判断：

- 通用 `v4.3` 可能比 `v4.2` 好
- 但若没有 code-specific 反证机制，依然很可能不够

### 3.3 当前 `v4.3` 容易失效的任务

#### `knowledge_crosswords`

高风险。

原因：

1. 它是 `structured_list / json_list` 任务，见 [profiles.py](/mnt/nvme/projects/R-HAN/mas_treesearch/profiles.py#L477)。
2. 错误经常是 slot-level、clue-level，而不是整条推理链整体错误。
3. 通用的局部分支扩张未必会自然对齐到“修某一个字段”。

判断：

- 如果不把 `v4.3` 改造成 slot-wise repair，它在 `knowledge_crosswords` 上很可能效果一般

#### `mmlu`

最不友好。

原因：

1. `mmlu` 是 `mcq / option` 任务，见 [profiles.py](/mnt/nvme/projects/R-HAN/mas_treesearch/profiles.py#L189)。
2. 选择题的核心瓶颈通常不是“局部搜索不够”，而是证据判断与短推理判断偏差。
3. 局部分支扩张 / restart 容易只增加成本，不产生真正新信息。

判断：

- `mmlu` 不适合成为 `v4.3` 主战场
- 更适合进入后续 `v4.4` 的 `Bypass / Lean / Full` 模式路由

## 4. 为什么 code task 需要专门版本

当前证据说明：

1. 在数学推理里，“与 anchor 不同”还有可能代表真正反证。
2. 在代码生成里，“与 anchor 不同”常常只是另一种错法。
3. 因此 code task 的 challenger 不能继续按自然语言推理任务的方式定义。

对 `humaneval / mbpp` 更合理的 challenger 定义应是：

1. 围绕 failed test 或可疑约束生成局部 patch 分支。
2. 让 verifier 给出“anchor 失败点”而不是只给全局判断。
3. 让 challenger 的资格依赖“修复了 anchor 的失败点”，而不是“语义上离 anchor 更远”。

## 5. 推荐的后续路线

### 5.1 不建议继续把所有任务压到单一 `v4.3`

更合理的做法是把 `v4.3` 拆成两条：

1. `v4.3-general`
   - 面向 `gsm8k`, `math`, `nlgraph`
   - 核心是局部分支扩张 + restart + 稀疏动态执行

2. `v4.3-code-structured`
   - 面向 `humaneval`, `mbpp`, `knowledge_crosswords`
   - 核心是 task-aware 的局部修复单元：
     - code task：failed test / patch / traceback 对应修复
     - structured task：slot / field / clue 级修复

### 5.2 `mmlu` 不应强行纳入 `v4.3`

`mmlu` 更适合：

- `v4.4` 的 budget-aware routing
- 多数样本直接 `Bypass`
- 少数不确定样本只走 `Lean Stage2`

而不是把它们都送进 `Full Stage2`

## 6. 结论

综合当前设计与实验现状，可以把方法与数据集的关系压缩成下表：

| 方法 | 最适合 | 部分适合 | 容易失效 |
|---|---|---|---|
| `v4.1` | `gsm8k` 安全基线 | `mmlu`, `nlgraph`, `knowledge_crosswords` | `humaneval`, `mbpp` 的长期提升 |
| `v4.2` | `gsm8k` 的 challenger 活性修补 | `nlgraph`, `mbpp`（待验证） | `humaneval`, `mmlu` |
| `v4.3-general` | `nlgraph`, `gsm8k` | `mbpp`, `humaneval` | `mmlu`, `knowledge_crosswords` |
| `v4.3-code-structured` | `mbpp`, `humaneval` | `knowledge_crosswords` | `mmlu` |
| `v4.4` budget-aware | `mmlu`，以及所有高成本任务 | 全部任务 | 无明显专属失效点 |

当前最重要的研究结论不是“继续统一方法”，而是：

- `v4.2` 已经证明 task-agnostic challenger 定义不够
- 后续必须按任务族拆分 stage2 机制
- 否则同一套 challenger 协议会在某些任务上工作、在另一些任务上系统性失效
