## 2. 一阶段设计方案

### 2.1 一阶段的定位

当前系统严格分成两层：

- `Stage1`：搜索“什么样的 MAS 结构最适合当前题目”。
- `Stage2`：在 `Stage1` 已冻结的 `UnionGraph` 上运行多轮执行、候选聚合与最终重判。

也就是说：

- `Stage1` 优化的是 `structure`
- `Stage2` 优化的是 `execution dynamics + final selection`

`Stage1` 结束后，真正传给 `Stage2` 的不是整棵搜索树，而是一份 `PreparedStage1Artifact`，其中包含：

- `union_graph`
- `stage1_output`
- `stage1_signature`
- `stage1_summary`
- `structure_summary`

这条边界很关键，因为它意味着二阶段的所有收益都必须建立在“固定结构上重新执行与重判”之上，而不是重新改图。

### 2.2 一阶段的输入、状态与输出

`Stage1` 的输入包括：

- `question_text`
- 可选 `reference_answer`
- `metadata`
- `dataset_name`
- `learn`
- `pipeline_mode`

核心中间状态是离散的 `ArchitectureState`，其本质上定义了三类对象：

- 工作流模板 `template`
- 角色到 agent 的分配 `role_to_agent`
- 角色 prompt slot 的配置 `role_to_prompt`

因此，`Stage1` 搜索的不是模型参数，而是 MAS 架构状态空间。

它最后输出的是 `SearchResult`，再被压缩成 `PreparedStage1Artifact`。

### 2.3 一阶段的主算法链

按照当前真实代码，`Stage1` 可以概括为下面这条链：

1. 解析数据集 profile，读取 `allowed_templates / root_templates / role_agent_preferences / structure_prior` 等先验。
2. 由 `TaskConditioner` 从 agent 池中选出本题相关的候选 agent 子集。
3. 按 `root_template` 构造若干初始结构状态 `s_root`。
4. 将结构状态编译为可执行图节点 `SearchNode`。
5. 枚举可扩展动作：
   - `change_template`
   - `swap_agent`
   - `set_prompt_slot`
   - `stop`
6. 若启用 `learned edit prior`，则先对动作排序。
7. 进入树搜索主循环：
   - 选 parent
   - progressive widening
   - 展开 child
   - 做 proxy evaluation
   - 对代码任务做 precheck
   - 对 top fraction 做 `tier1`
   - 对更小子集做 `tier2`
   - 用 `tier2 reward` 回传到搜索树
   - 如启用学习，则更新 `value model` 与 `edit prior`
8. 搜索结束后，对 finalists 做一次兜底 `tier2` 重评，确定 `best_node`。
9. 并不直接拿单图，而是用 `TopologySetScorer` 从高分图中选一组“高质量且互补”的拓扑。
10. 用 `GraphMerger` 把多张图合成带统计量的 `UnionGraph`。
11. 生成 `structure_summary` 并打包为 `PreparedStage1Artifact`。

### 2.4 一阶段各关键设计点

#### 2.4.1 parent 选择不是纯贪心

`Stage1` 的 parent 选择同时结合：

- root restart
- 高分节点优先
- PUCT 风格 bonus

因此它不是简单 best-first，而是“带探索的高分优先搜索”。

#### 2.4.2 结构动作空间是离散、可解释的

它搜索的不是连续控制，而是非常清楚的结构操作：

- 换模板
- 换角色 agent
- 改 prompt slot
- 停止扩展

这使得一阶段的搜索轨迹和最终结构具有较强可解释性。

#### 2.4.3 评估是分层的

`Stage1` 不是对所有结构一上来就跑高成本评测，而是：

- 先 `proxy`
- 再 `precheck`
- 再 `tier1`
- 最后 `tier2`

这种分层评测设计使得它能在较大离散结构空间里维持可用的计算效率。

#### 2.4.4 最终交给二阶段的不是单图，而是合图

这一步很重要。`Stage1` 不是简单输出一个 `best_node` 的 compiled graph，而是先做“拓扑集合选择”，再合成为 `UnionGraph`。因此二阶段拿到的是：

- 已经过结构层多样性筛选的图
- 节点和边上带有 `support_ratio / avg_parent_score / initial_keep_logit` 等统计先验的图

这也是为什么 `Stage2` 不是从零开始，而是站在一个已经很强的结构锚点之上。

### 2.5 一阶段为什么会成为强锚点

从保存下来的 selected runs 可以看出，一阶段本身已经很强：

- `gsm8k`：确认的 `success = 0.9754`
- `humaneval`：确认的 `success = 0.8855`
- `mbpp`：当前保留证据对应约 `0.8427`

参考材料见：

- [`../stage1_selected_runs_20260330/README.md`](../stage1_selected_runs_20260330/README.md)

这意味着二阶段面对的不是一个弱 baseline，而是一个已经接近 ceiling 的强 anchor。后续几乎所有二阶段退化，本质上都和这个高基线条件有关。

## 3. 二阶段的初始目标与根本困难

### 3.1 二阶段原始想解决什么

`Stage2` 的原始愿景是：

1. 在固定 `UnionGraph` 上运行多轮交互。
2. 借助 `GNN + global node + latent memory` 重新组织消息流。
3. 从多轮输出中构造 candidate bank。
4. 让系统在“保留 `stage1 anchor`”和“用更好的 `stage2 candidate` 覆盖它”之间做更优决策。

### 3.2 当前执行壳的关键约束

从 `runtime_v2` 和 `v3/v3.1` 的真实实现看，当前二阶段虽然会做边 pruning，但仍保留一个重要性质：

- 所有 task nodes 每轮都会执行。

也就是说，当前真实执行壳仍然更接近：

`固定图上的全量多轮传播 + 末端重判`

而不是：

`围绕失败点的局部动态搜索`

这正是后续 `v4.3` 试图改变、但目前只部分改变成功的地方。

### 3.3 二阶段退化的总根因

到目前为止，可以把二阶段的退化归结为四条主因：

1. `Stage1` anchor 太强，弱 challenger 没有容错空间。
2. candidate bank 有“重复即高分”的统计惯性，少数异见容易被淹没。
3. 最终判别器在高基线条件下容易出现：
   - 要么过度保守，不敢翻案
   - 要么高置信翻错案
4. 对 code / graph / reasoning 任务，“什么叫 challenger”根本不是同一件事。

前两版 `v4.1 / v4.2` 主要修的是第 2 和第 3 点；当前 `v4.3` 才开始真正触及第 4 点。

## 4. 二阶段优化迭代总览

| 版本 | 主要改动 | 目标 | 主要表现 | 暴露的问题 |
|---|---|---|---|---|
| `v3` | `candidate_model + override_model + reviewer_model` | 在固定图上学会候选排序与覆盖决策 | 在 `gsm8k` 早期快照中 override 基本塌缩为 0 | 高基线下 override 监督严重失衡，系统学成 preserve-only |
| `v3.1` | 重构为 `候选绝对质量 + pairwise 相对优势 + reviewer 相对校准` | 避免 `v3` 的绝对分数卡死与 override 头塌缩 | `gsm8k` 上总体反而负增益，发生大量有害翻案 | challenger 质量不够，pairwise 高置信但方向错 |
| `v4.1` | 显式 challenger + DAR 式保留 + 更严格 override 资格 | 先压住有害 override | `gsm8k` 上 `override_count = 0`，成功压住错翻 | 系统退化为 preserve-only，challenger 饥饿 |
| `v4.2` | Auditor 软晋升 challenger + ACH 仲裁 + permutation calibration | 放宽 challenger 供给，并让仲裁更结构化 | `gsm8k` 稍微“活”起来；`humaneval` 几乎完全不起 challenger | 对 code task 的 challenger 定义失配，selection-side 修补不够 |
| `v4.3` | 从语义仲裁转向 verifier 驱动的 `code-repair` 局部搜索 | 让 code task 出现真正可验证的 challenger | 已出现至少一次有益 repair overturn | 当前仍是 preserve 主导，且实现仍是 `code-repair-first` 的部分落地 |

## 5. 分版本详细总结

### 5.1 `v3`：在固定图上学习候选排序与 override

`v3` 的核心结构是：

- 固定 `Stage1 -> UnionGraph`
- `runtime_v2` 多轮执行壳
- `candidate_model`
- `override_model`
- `reviewer_model`

它想做的事很直接：

1. 通过多轮图执行产生 candidate bank。
2. 对 candidate 估质量。
3. 判断是否值得 override `stage1 anchor`。

但在 `gsm8k` 的早期快照中，`override_model` 很快就塌成了几乎永不触发。这说明：

- 当 `stage1` 已经很强时，`override_target = 1` 的正样本极少。
- `override_model` 容易直接学成“默认别动 stage1”。

因此 `v3` 的主要失败不是“实现坏了”，而是监督目标在高基线条件下天然失衡。

### 5.2 `v3.1`：从绝对分数兜底改成相对优势判断

`v3.1` 的目标是纠正 `v3` 的几个核心问题：

1. 不再让 `candidate_model` 先把 challenger 卡死，再由 `override_model` 被动兜底。
2. 不再让 reviewer 只围绕候选自身“像不像好答案”打分，而是围绕“相对 anchor 是否有纠错价值”做校准。
3. 用同一套相对比较逻辑同时覆盖 `gsm8k` 的保守和 code task 的激进问题。

从设计上看，`v3.1` 的核心链是：

`Q(c) + P(c > anchor) + reviewer relative calibration`

而不是旧的：

`绝对排序 -> 单个 challenger -> override`

#### 5.2.1 `v3.1` 的实验现象

`v3.1` 的失败模式不是保守，而是“高置信错翻”。

在 [`v4_design.md`](./v4_design.md) 总结的 `gsm8k` 口径中：

- 训练样本：`264`
- `stage1_success = 0.9697`
- `stage2 final success = 0.8902`
- `selection_decision = use_stage2_pairwise`：`25`
- 这 `25` 次 override 全部失败
- 其中 `21` 次是“`stage1` 本来正确，但 `stage2` 覆盖后变错”

而在 [`../docs/stage1_stage2_overview_and_stage2_bottlenecks_20260403.md`](../docs/stage1_stage2_overview_and_stage2_bottlenecks_20260403.md) 的另一个时间截面里，已经能看到相同方向的证据：

- override path 的 `pairwise probability mean = 0.7416`
- 但 override path 的 `stage2_success = 0.0`

这两个统计口径不同，但结论一致：

- `v3.1` 不是不敢翻案
- 而是一旦翻案，经常高置信地翻错

#### 5.2.2 `v3.1` 失败说明了什么

`v3.1` 失败的关键不在于 pairwise 模型容量不够，而在于：

1. candidate bank 里本来就缺强 challenger。
2. 重复答案在 bank 中有统计优势。
3. pairwise 学到的是“像多数路线的 challenger 更可信”，而不是“真能纠正 anchor 的 challenger 更可信”。

这就是 `v4` 路线必须从“先消除有害 override”开始，而不是继续堆更复杂判别器的原因。

### 5.3 `v4.1`：先压住有害 override

`v4.1` 的三项核心改动是：

1. 显式 challenger
2. DAR 式消息保留
3. 更严格的 override 资格

它的目标很明确：

- 不是让 override 更多
- 而是先把 `v3.1` 里的有害 override 压住

#### 5.3.1 `v4.1` 的表现

在 `gsm8k / train` 上：

- 样本数：`264`
- `avg_success = 0.9697`
- `override_count = 0`
- `explicit_positive = 3`

主要 preserve 原因：

- `v4_1_preserve_no_explicit_challenger`: `261`
- `v4_1_preserve_inspector`: `1`
- `v4_1_preserve_pairwise`: `2`

#### 5.3.2 `v4.1` 的意义与问题

`v4.1` 的意义：

- 它基本完成了“压住有害 override”的目标。
- 它证明“先安全、再放宽”的顺序是对的。

`v4.1` 的新问题：

- 系统极易退化为 preserve-only。
- 显式 challenger 太稀少。
- 资格制过于依赖“先有 challenger 出现”这个前提。

因此 `v4.1` 是一个必要的安全基线，但不是长期主线。

### 5.4 `v4.2`：放宽 challenger 供给，但仍停留在 selection-side 修补

`v4.2` 的主要改动是：

1. 用 auditor 软晋升 `provisional challenger`
2. 用 ACH 风格结构化仲裁替代简单 pairwise
3. 在 override 前做 permutation calibration

它的本质仍然是：

- 在最终选择链路上修补
- 而不是重写执行动力学

#### 5.4.1 `gsm8k / v4.2`

`gsm8k / train`：

- 样本数：`264`
- `avg_success = 0.9659`
- `override_count = 0`
- `explicit_positive = 4`
- `provisional_positive = 7`
- `adjudication_paths = 7`
- `calibration_positive = 0`

`gsm8k / test`：

- 样本数：`1055`
- `avg_success = 0.9706`
- `override_count = 1`
- `provisional_positive = 21`
- `adjudication_paths = 21`
- `calibration_positive = 1`

唯一一次 override 还是有害翻案：

- `id = gsm8k:official_test:1016`
- `reason = v4_2_override_calibrated_challenger`
- `success = 0.0`

#### 5.4.2 `humaneval / v4.2`

`humaneval / train`：

- 样本数：`33`
- `avg_success = 0.8485`
- `override_count = 0`
- `explicit_positive = 0`
- `provisional_positive = 0`

并且训练与测试当前样本几乎都只有一类 preserve 原因：

- `v4_2_preserve_no_provisional_challenger`

#### 5.4.3 `v4.2` 的结论

`v4.2` 在 `gsm8k` 上比 `v4.1` 更“活”：

- 它确实让一小部分样本进入了 `provisional challenger -> adjudication -> calibration`

但它没有形成有效收益：

- `gsm8k` 上几乎没有真实有效翻案
- `humaneval` 上甚至一个 `provisional challenger` 都起不来

这说明：

1. selection-side 修补只能解决表面的“完全僵住”。
2. 对 code task 来说，问题已经不是“门槛过高”，而是“challenger 资格定义本身错位”。

这直接把路线推向了 `v4.3`。

### 5.5 `v4.3`：从语义仲裁转向 verifier 驱动的局部修复

`v4.3` 是当前最关键的一版，需要把“设计目标”和“已落地实现”分开理解。

#### 5.5.1 `v4.3` 的设计目标

在设计文档 [`v4_design.md`](./v4_design.md) 中，`v4.3` 的核心转向是：

- 不再围绕 finalizer 做文章
- 不再把 challenger 定义为“语义上更不同的答案”
- 转而把 `Stage2` 改造成 verifier-triggered local search

它的统一抽象是：

`Detect -> Localize -> Expand -> Execute + Verify -> Select -> Restart`

对 code task，challenger 的定义变成：

- 不是另一段“看起来更好”的全文代码
- 而是能够修复当前 anchor 已知失败点的局部候选

#### 5.5.2 当前 `v4.3` 的真实落地形态

当前真实落地的不是完整通用版 `v4.3`，而是：

- `v4.3-code-repair`
- `mbpp-first`

并且它仍然具有两个很重要的现实边界：

1. 代码实现上仍然复用 `runtime_v2` 的执行骨架，`run()` 里仍是“所有 task nodes 每轮执行”。
2. 只有 `code_generation` 任务会走新的 `code_repair` finalizer；非 code task 当前仍回退到 `v4.2` 路径。

也就是说，当前 `v4.3` 是：

- 一个针对 code task 的局部重构
- 而不是已经完全实现了设计稿中的通用 `GEF-Loop`

这点必须写清楚，否则会高估当前版本的完成度。

#### 5.5.3 当前 `v4.3` 的真实实现机制

按照 [`../mas_stage2_v4_3/runtime.py`](../mas_stage2_v4_3/runtime.py) 和 [`../mas_stage2_v4_3/code_repair.py`](../mas_stage2_v4_3/code_repair.py)，当前实现可以概括为下面这条链：

1. 先像旧版一样运行 `runtime_v2` 多轮图执行，拿到 candidate bank。
2. 若任务不是 `code_generation`，直接回退到 `v4.2` 的 finalizer。
3. 若任务是 `code_generation`，则不再直接做语义仲裁，而是先对：
   - `stage1 anchor`
   - stage2 候选
   做可执行验证。
4. 每个代码候选通过 `evaluate_code_candidate(...)` 得到 `CodeRepairEval`，其中关键验证项包括：
   - `syntax_ok`
   - `entry_point_ok`
   - `passed / total`
   - `failure_kind`
   - `failing_examples`
5. 支配关系不再是一个人工加权总分，而是偏序关系：
   - `dominance_tuple = (syntax_ok, entry_point_ok, passed)`
   - 只有当一个候选逐项不差且至少一项更优时，才视为 `dominates(...)`
6. 系统会构造一个 verified seed pool：
   - 取 top-k 已验证候选
   - 默认 `repair_seed_top_k = 4`
   - 若 anchor 没在 top-k 中，也会强制保留 anchor
7. 若最优 verified seed 不能支配 anchor，则直接 preserve anchor。
8. 若当前选中的 seed 还没 fully pass，则启动 repair loop：
   - 由 `coder / planner / debater_a` 作为 repair agents
   - 读取 failure summary
   - 生成 patch-like 分支
9. 对 repair branches 重新执行验证：
   - 若某个 patch 支配当前 checkpoint，则升级为新 checkpoint
   - 否则允许 restart 到下一个 verified seed
10. repair 轮数耗尽后，再做一次最终 guard：
    - 如果最终所选候选并不支配 anchor，则回退为 `v4_3_code_preserve_anchor_superior`

因此，当前 `v4.3` 最重要的学术含义在于：

- 它第一次把 code task 中的 challenger 定义成“可执行验证下的严格改进”
- 而不是“语义上看起来比 anchor 更像对的代码”

#### 5.5.5 `v4.3` 当前日志前缀又说明了什么

与此同时，日志已经跑到了 `46/195`，但 checkpoint 只保存到 `25` 条。因此还需要看日志前缀的行为分布。

1. beneficial overturn 已经出现，但频率仍然很低。
2. 很多样本虽然触发了 repair branches / restart，但最后仍无法在 verifier 关系下支配 anchor。

典型例子包括：

- challenger 已经开始以 patch 形式出现
- 但它们大多数还不够强，无法形成稳定、广泛的 strict improvement

#### 5.5.6 当前 `v4.3` 已经解决了什么

当前 `v4.3` 至少已经解决了两件 `v4.2` 解决不了的事：

1. 它让 code task 中真正出现了 verifier-backed challenger。
2. 它已经产生了至少一个由 repair 分支带来的有效翻案样本。

这两个事实很重要，因为它们说明：

- 对 code task，正确方向不是继续放宽语义仲裁
- 而是把 challenger 重新定义为“围绕已知失败点的局部修复候选”

#### 5.5.7 当前 `v4.3` 还没有解决什么

当前 `v4.3` 仍然存在四个明显瓶颈：

1. `preserve` 仍是绝对主导行为。
2. 当前实现仍运行在旧执行壳上，尚未真正做到 task-aware sparse execution。
3. correctness 有局部正证据，但 reward 维度依然显著为负，效率非常差。
4. 当前只验证了 `mbpp-first` 的 code-repair 子线，还不能推出通用 `v4.3` 已经成立。

因此当前 `v4.3` 更准确的结论应当是：

- **方向已被验证**
- **但覆盖率和效率都还远未验证成功**

#### 5.5.8 对当前 `v4.3` 的学术定位

如果从学术角度总结，当前版本的价值不在于“它已经全面超过一阶段”，而在于它完成了一个关键范式转移：

- `v4.1 / v4.2` 修的是“谁有资格在最后一刻挑战 anchor”
- `v4.3` 开始修“challenger 在执行过程中如何以 verifier-backed 的方式被生成出来”

这一步是否打通，决定了后续 `v4.4 / v4.5 / v4.6` 是否有意义。

如果连 code task 的真正 challenger 都起不来，那么再做：

- budget-aware routing
- turn-level credit assignment
- coordinator / RL

最终也只会学出更保守的 preserve 行为。

### 5.6 `v4.4 / v4.5 / v4.6`：已进入设计，但尚无正式实验结论

当前设计文档里还保留了三条后续路线：

- `v4.4`：任务感知的协议路由 + 预算感知模式选择
- `v4.5`：基于可验证进展的事件级 credit assignment
- `v4.6`：分层协调器与 RL / MARL

但到本文更新时间为止，这三版仍应视为：

- **设计路线已明确**
- **实验结论尚未形成**

因此它们在本文中的位置主要是“后续研究计划”，而不是“已经完成并可比较的版本结果”。

## 7. 当前阶段的综合结论

截至目前，可以把整个项目压缩成三条最重要的结论：

### 7.1 一阶段已经足够强，二阶段不能再靠“末端打分修补”

因为 `Stage1` 已经产出非常强的 anchor，所以：

- 弱 challenger 没有容错空间
- 单纯改 finalizer 往往要么 preserve-only，要么高置信错翻

这也是为什么 `v3.1 -> v4.1 -> v4.2` 都没有形成稳定增益。

### 7.2 不同任务上，“什么叫 challenger”完全不同

- 对 `gsm8k / math`，challenger 更接近竞争性假设。
- 对 `mbpp / humaneval`，challenger 更接近修复已知失败点的 patch。
- 对 `nlgraph`，challenger 更接近修复局部结构断裂的 block。

因此后续路线必须从“统一协议”转向“任务 affordance 驱动的协议分化”。

### 7.3 当前 `v4.3` 是真正的分水岭，但仍只完成了第一步

当前 `v4.3` 的真实状态应当这样理解：

- 它首次在 code task 上证明了 verifier-backed repair overturn 是可能发生的。
- 它说明方向是对的：应从语义仲裁转向执行驱动的局部修复。
- 但它还没有证明当前实现已经能在总体指标上稳定超过一阶段。

更严格地说：

- `v4.3` 已经验证了“机制方向”
- 尚未验证“整体有效性”
