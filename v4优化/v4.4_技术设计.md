# Stage2 V4.4 技术设计

更新时间：2026-04-09

## 1. 目标

`v4.4` 的目标不是再发明一个更聪明的总分，而是把 `stage2` 硬化成一条清晰、离散、可验证的协议链：

`CollapseClasses -> AffordanceRoute -> SparseActivate -> HardDominance / ACH-Lexicographic -> AnchorGuard`

这版设计坚持四条原则：

1. 不引入跨任务统一的连续加权总分。
2. 预算只决定跑多深，不决定谁更好。
3. code / graph 任务优先依赖 verifier；reasoning 任务优先依赖结构化证据淘汰。
4. `anchor` 仍然是最终守门人，所有 override 都必须通过 route-specific 的 hard guard。

## 2. 不在本版内的内容

`v4.4` 明确不包含：

- `GTPO`
- `Dr. MAS`
- learned coordinator
- preserve penalty
- 多参数 reward shaping

它们属于 `v4.5 / v4.6` 的范围，不提前并入 `v4.4`。

## 3. 总体算法

对样本 `x`、一阶段锚点 `a`、原始候选集合 `C_raw`、预算桶 `b ∈ {tight, normal, ample}`，`v4.4` 的主流程为：

1. `V <- VerifyAll({a} ∪ C_raw)`
2. `Classes <- CollapseClasses(V)`
3. `p <- RouteFamily(x)`，输出协议族 `p`
4. `m <- RouteMode(a, Classes, b)`，输出执行模式 `m`
5. 若 `m = Bypass`，直接执行 `AnchorGuard(a)`
6. 否则，按 `(p, m)` 构造活跃子图 `Active <- SparseActivate(...)`
7. 执行 route-specific 协议：
   - `Code-Repair`
   - `Graph-Constrained`
   - `Adversarial`
8. 只有当候选通过 route-specific hard guard 时，才允许覆盖 `anchor`

最终输出不只是答案，还包括协议轨迹：

`tau_4 = (protocol_family, execution_mode, budget_bucket, n_classes, n_active_nodes, n_branch, n_restart, anchor_used)`

## 4. CollapseClasses

### 4.1 设计目的

在路由和仲裁之前，先折叠 candidate bank 中的重复等价类。这样做的作用是：

1. 阻止“重复答案在 bank 中获得统计优势”。
2. 让少数但结构上不同的 challenger 获得独立生存空间。
3. 让后续的 `RouteMode` 与 `ACH` 基于“独立假设类”而不是“文本重复次数”。

### 4.2 等价类 key

按协议族定义不同的等价类 key。

#### `Code-Repair`

`key_code = (syntax_ok, entry_point_ok, passed, total, failure_kind, patch_locus)`

其中：

- `syntax_ok` 与 `entry_point_ok` 来自可执行验证。
- `passed / total` 来自可见测试通过情况。
- `failure_kind` 来自 verifier 输出。
- `patch_locus` 来自主失败样例或主失败类型。

#### `Adversarial`

`key_reason = (normalized_answer, fatal_contradiction_set, contradiction_cluster)`

其中：

- `normalized_answer` 是任务格式归一化后的核心结论。
- `fatal_contradiction_set` 记录致命格式冲突或硬违约。
- `contradiction_cluster` 记录当前主冲突簇，例如：
  - `invalid_option`
  - `missing_numeric_target`
  - `empty_math_expression`
  - `unsupported_yes_no`

#### `Graph-Constrained`

`key_graph = (broken_block_set, repair_locus, normalized_structure)`

其中：

- `broken_block_set` 是局部结构断裂块集合。
- `repair_locus` 是当前最优先修补块。
- `normalized_structure` 是格式归一化后的局部结构表示。

### 4.3 代表元选择

每个等价类只保留一个 representative。

选择规则不使用频次总分，而使用 route-specific 的词典序：

- `Code-Repair`：按 verifier rank key，再按 quality / review 轻量 tie-break。
- `Adversarial`：按 fatal 最少、major 最少、critical support 最多，再按 quality tie-break。
- `Graph-Constrained`：按 broken blocks 最少、verified blocks 最多，再按 quality tie-break。

`class_size` 只保留在元数据中，最多作为最后一级 tie-break，不参与主排序。

## 5. AffordanceRoute

### 5.1 RouteFamily

协议族由任务 affordance 决定，而不是按 benchmark 名字硬编码。

定义三个谓词：

- `ExecOracle(x)`：是否有可执行程序与显式执行反馈。
- `LocalConstraint(x)`：是否有局部结构约束检查器。
- `HypothesisTest(x)`：是否主要依赖竞争性假设检验。

则：

1. 若 `ExecOracle(x) = 1`，则 `protocol_family = Code-Repair`
2. 否则若 `LocalConstraint(x) = 1`，则 `protocol_family = Graph-Constrained`
3. 否则，`protocol_family = Adversarial`

当前自然映射为：

- `mbpp`, `humaneval` -> `Code-Repair`
- `nlgraph`, `knowledge_crosswords` -> `Graph-Constrained`
- `gsm8k`, `math`, `mmlu`, `normad` -> `Adversarial`

### 5.2 RouteMode

`v4.4` 使用完全离散的 mode gate：

- `StableAnchor`
- `ResolvableConflict`
- `StrongConflict`

定义如下：

#### `StableAnchor`

满足以下条件之一：

1. `anchor` 处于该 route 的最高验证层级。
2. 所有非 anchor class 要么硬失败，要么没有提出新的 fatal counter-evidence。

则：

`StableAnchor -> Bypass`

#### `ResolvableConflict`

满足以下条件之一：

1. 只存在一个 surviving non-anchor class。
2. 只存在一个主失败点或一个主冲突簇。

则：

`ResolvableConflict -> Lean`

#### `StrongConflict`

满足以下条件之一：

1. 至少存在两个相互独立的 surviving challenger classes。
2. `anchor` 在当前 route 的硬验证中出现重复失败或明显的多点冲突。

则：

`StrongConflict -> Full`

### 5.3 预算的作用

预算只允许向下压缩模式，不允许抬高候选质量。

规则固定为：

1. `tight`：`Full -> Lean`，必要时 `Lean -> Bypass`
2. `normal`：保留原 mode
3. `ample`：保留原 mode，但不因为预算大而放宽 hard guard

因此 budget 是外层 gate，不进入候选优劣排序。

## 6. SparseActivate

### 6.1 核心定义

节点发声资格被硬化为：

`Speak(node) = RoleMatch ∧ TouchesFailureLocus ∧ AddsNovelSignal`

其中：

- `RoleMatch`：角色与当前 route / mode 匹配。
- `TouchesFailureLocus`：节点触达当前失败点或冲突簇。
- `AddsNovelSignal`：不是简单复读，能够提供新的 patch / 新证据 / 新假设。

### 6.2 route-specific 激活

#### `Code-Repair`

只激活：

- verifier / critic / judge
- solver / generator / reviser 这类 repair roles
- 必要时的 router / aggregator

Lean 模式下限制为少量 repair roles；Full 模式下允许更宽的 repair branch 子集。

#### `Graph-Constrained`

只激活：

- block checker
- local repairer
- 必要的 aggregator

并且默认只围绕当前 `repair_locus` 的一跳邻域工作。

#### `Adversarial`

只激活：

- hypothesis proposer
- evidence extractor
- cross examiner

Lean 模式只保留少量 top hypotheses；Full 模式允许更宽的 challenger class 集。

### 6.3 当前版本的实现边界

本版 `SparseActivate` 直接接入现有 `runtime_v2._active_task_nodes_v2(...)` 钩子：

1. 先继承 edge pruning 后的 base active set。
2. 再按 route family、mode、上一轮 feedback target 和 role novelty 继续裁剪。
3. 不改一阶段图结构，也不重新搜索 UnionGraph。

## 7. Code-Repair 协议

### 7.1 Bypass

1. 对 `anchor` 做硬验证。
2. 若 `anchor` 已处最高验证层级，直接保留。

### 7.2 Lean

1. 对 `{anchor} ∪ C` 执行 `VerifyAll`
2. 做 `CollapseClasses`
3. 只保留一个最优 verified seed
4. 做一轮 repair branch 扩张
5. 若存在严格支配当前检查点的 patch，则更新检查点
6. 末尾仍需通过 `AnchorGuard`

### 7.3 Full

1. 构造多种子池
2. 允许多轮 repair branch 扩张
3. 允许 verified seed restart
4. 只接受 verifier strict dominance

### 7.4 Inspector-on-Promotion

该机制只属于 `Code-Repair` route，不扩展为全局 judge。

当某个 patch branch 支配当前检查点、但尚未 fully pass 时，先执行：

`InspectorApprove(branch, primary_failure_locus) ∈ {0, 1}`

Inspector 只回答：

1. 主失败点是否真的被修掉。
2. 是否引入新的接口漂移 / 语义漂移。

只有 `InspectorApprove = 1` 时，才允许 branch 晋升为新检查点。

## 8. Graph-Constrained 协议

### 8.1 状态

记：

`sigma_graph = (G, U, B_break, repair_locus)`

其中：

- `G`：当前结构候选
- `U`：局部块分解
- `B_break`：断裂块集合
- `repair_locus`：当前主修补块

### 8.2 Bypass

若 `anchor` 格式稳定且没有 surviving challenger class，则直接 preserve。

### 8.3 Lean

1. 验证 `{anchor} ∪ C`
2. 折叠等价类
3. 只保留一个主修补块
4. 选择局部约束更好的 representative
5. 通过 `AnchorGuard`

### 8.4 Full

1. 允许围绕 `repair_locus` 额外生成少量 repair candidates
2. 只接受 broken blocks 更少、且不破坏已满足块的候选
3. 若无法继续改进，可回退到上一个局部稳定检查点

## 9. Adversarial 协议

### 9.1 状态

记竞争性假设集合为：

`H = {h_0, h_1, ..., h_k}`

其中 `h_0` 通常对应 `anchor`。

### 9.2 ACH-Lexicographic

`v4.4` 不再统计软性“反驳强度总分”，而改成三层证据优先级：

- `fatal evidence`
- `major evidence`
- `minor evidence`

淘汰规则固定为：

1. 命中 `fatal contradiction` 的假设直接淘汰
2. 在剩余假设中，优先选择 `major contradiction` 最少者
3. 若仍平手，选择 `critical support` 最多者
4. 若最终只剩 `anchor` 与 challenger 难分，再调用 `CalibraEval`

### 9.3 CalibraEval 的位置

`CalibraEval` 不作为主引擎，只作为最后 tie-case 的去偏校准。

它只在以下情况触发：

1. 经过 ACH 词典序淘汰后，`anchor` 与单个 challenger 难分
2. challenger 不是 fatal
3. challenger 已通过前面的硬性淘汰

## 10. AnchorGuard

`v4.4` 的最终 guard 依旧严格保留：

- `Code-Repair`：只有严格支配 `anchor` 才可 override
- `Graph-Constrained`：只有局部约束严格更优且无新增 fatal block 才可 override
- `Adversarial`：只有 ACH 词典序占优，且必要时经 `CalibraEval` 去偏后仍占优，才可 override

否则一律 preserve `anchor`。

## 11. 与文献的对应

### 11.1 直接进入主体

- `DAR`：支撑 `CollapseClasses` 和保留 disagreement
- `PAMAS`：支撑 minority signal 先聚类、再路由
- `CortexDebate`：支撑 `SparseActivate`
- `Faulty Agents`：支撑 `Challenger / Inspector` 的轻量 promotion gate
- `CalibraEval`：支撑 tie-case 去偏校准

### 11.2 只借思想

- `BATS`：只借预算感知作为 mode outer gate
- `MALT`：只借 `Full` 模式下的小规模局部分支扩张

### 11.3 暂不纳入

- `GTPO`
- `Dr. MAS`
- learned coordinator

## 12. 本版验证重点

`v4.4` 最关键的 ablation 只有三组：

1. `+ CollapseClasses`
2. `+ SparseActivate`
3. `+ ACH-Lexicographic`

如果这三组都不能带来可见收益，再考虑是否继续走 `v4.5`。
