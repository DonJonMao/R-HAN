## 2. `v4.1` 与 `v4.2` 的设计目标

### 2.1 `v4.1` 解决什么

`v4.1` 的目标不是“让 override 更多”，而是先把 `v3.1` 中有害的 override 压住。

它做的事情可以概括为三条：

1. 增加显式 challenger 通道，而不是只依赖普通 task nodes 自发给出替代答案。
2. 用 DAR 式消息保留，尽量保留异见而不是只保留重复高分答案。
3. 把 override 资格变得更严格，避免弱 challenger 错翻强 anchor。

因此，`v4.1` 的成败标准不是“翻案次数”，而是“先不要错翻”。

### 2.2 `v4.2` 解决什么

`v4.1` 暴露出的新问题是：系统过于容易退化成 preserve-only。

`v4.2` 的目标因此转成了三件事：

1. 让 challenger 不必只靠固定显式 agent 命中，而是允许 candidate bank 中少数派答案在 auditor 支持下被软晋升为 `provisional challenger`。
2. 让 finalizer 不再只是一次 pairwise，而是进入 ACH 风格的结构化仲裁。
3. 在最终 override 前做 permutation calibration，防止“高置信但方向错”。

需要强调的是：`v4.2` 本质上仍然是 selection-side / adjudication-side 修补，而不是 execution-side 重构。

## 4. 现阶段综合判断

### 4.1 `v4.1` 的价值

`v4.1` 的价值是：

- 它先把 `v3.1` 里危险的错误 override 压住了
- 它证明“先保证安全，再谈放宽”这个顺序是对的

但它的主要瓶颈也很明确：

- 系统极易退化为 preserve-only
- challenger 供给太少

### 4.2 `v4.2` 的价值

`v4.2` 的价值是：

- 它验证了 soft promotion / adjudication / calibration 这条链不是完全静态的
- 在 `gsm8k` 上，这条链路确实被激活过

但 `v4.2` 当前的局限也已经清楚：

1. 在 `gsm8k` 上，“能走到审议”不等于“能有效翻案”。
2. 在 `humaneval` 上，连 soft promotion 都没有被激活。
3. 因此 `v4.2` 更像是对 selection-side 的修补，而不是对 challenger 质量本身的修复。

### 4.3 当前最重要的诊断结论

截至目前，最关键的诊断不是“模型不够强”，而是：

1. `v4.2` 对强 anchor 的数值推理任务只带来了有限的 challenger 活性提升。
2. `v4.2` 对 code task 的 challenger 定义存在明显失配。
3. 因而如果 `mbpp` 继续延续 `humaneval` 的模式，那么应直接判定：
   - 不能继续围绕 `v4.2` 的资格与仲裁定义小修小补
   - 应进入 `v4.3`，从执行动力学层面重构 challenger 的形成过程

## 5. 为什么 `v4.2` 在 code task 上失配

当前 `v4.2` 的参考来源中，最直接影响 soft promotion 的是 PAMAS 风格 auditor 聚合；但这类方法的原始实验并不在 code generation 上。

例如 [`pamas.pdf`](/mnt/nvme/projects/R-HAN/v4优化/gemini辩论/pamas.pdf) 的实验数据集是：

- Amazon
- DeRev2018
- PolitiFact

它验证的是“少数派异常视角的聚合”在 misinformation detection 中有效，并没有证明：

- `HumanEval` 上与 anchor 语义不同的程序就更可能是有效 challenger
- `MBPP` 上少数派候选就能构成真正可执行的反证

因此，`v4.2` 在 code task 上失败，不应理解为“参考论文错了”，而应理解为：

- 我们把一个适用于文本异常检测 / 观点聚合的机制，迁移到了代码生成
- 但代码任务真正需要的是“可执行反证”，不是“语义异常”

## 6. 下一步建议

在当前证据下，下一步建议是：

1. 跑完 `mbpp`
   - 它仍然值得作为最后一个 code task 验证点
   - 因为它比 `humaneval` 更短、更局部、测试反馈更显式

2. 若 `mbpp` 也接近 `0 override`
   - 则可正式停止继续打磨 `v4.2`
   - 进入 `v4.3`

3. `v4.3` 不应只是“放宽更多门槛”
   - 它应把 challenger 从“候选筛选问题”转成“局部分支扩张与反证生成问题”

4. 对 code task，`v4.3` 还应进一步分化为 code-specific 版本
   - 让 challenger 围绕 failed test / 局部 patch / 局部程序修复展开
   - 而不是继续依赖通用的语义差异 + 审计晋升
